# Trend Atlas 有界只读代码审查

范围：`lib/feed.ts`、`lib/adapters.ts`、`lib/explore.ts`、`components/trend-app.tsx`；另读取类型、分类、来源定义与 API 入口以确认调用关系。未修改网站、未启动项目、未调用 Sites，也未运行以下复现。下面是读取时版本的静态审查结论；主代理仍在修改，修复后应以新版本重新确认。

## 1. [P2] 无效条目或 HN 子请求失败会制造来源名次上升

**证据：** `lib/adapters.ts:20-28` 先删除无效标题、URL 与重复条目，再使用清洗后的索引 `i + 1` 写入 `rank` 和历史。`lib/adapters.ts:54-55` 对 HN 的 16 个请求使用 `Promise.allSettled`，直接丢弃失败项。`lib/feed.ts:17` 用这些名次形成 `previousRank`；`lib/explore.ts:11-14` 将变小的名次放入上升榜。

**实际后果：** 原来位于源榜 #2 的同一故事，如果 #1 的请求在下一轮失败，就会变成本站显示的“源榜 #1”，并被显示“上升 1”。上游实际顺序可以完全未变；其他来源中一条失效链接也会造成同样结果。这与“保留平台原始名次”的展示口径不一致。

**最小修复：** Raw 保留原始榜单位置；HN 在映射请求结果时携带 `ids` 的原始索引。来源名次与历史使用该位置；有效样本中的位置分可以另行计算，不用清洗后的序号冒充来源名次。部分采集失败要在来源状态中说明。

**验证：** 两轮上游 ID 顺序相同，第二轮让首条子请求失败；第二条源榜名次保持 #2，不进入上升榜。

## 2. [P2] 60s 回退到访客 UAPI 后仍每 10 分钟消耗一次配额

**证据：** `lib/adapters.ts:63-67` 在 60s 失败时调用 UAPI 并返回 `channel="UAPI · 备用聚合"`。`lib/feed.ts:56` 的 6 小时更新条件仅检查 `source.adapter === "uapi"`，因此实际使用 UAPI 的 `sixty` 来源仍获得 10 分钟 TTL；失败退避 `lib/feed.ts:63` 也同样按配置 adapter 判断。访客预算在 `lib/feed.ts:39-41` 限为每天 40 次。

**实际后果：** 60s 持续失败、UAPI 备用成功时，最多 5 个备用来源每轮消耗 5 次访客请求；约 8 轮就可耗尽一天预算，远快于页面说明的“UAPI 访客源每 6 小时更新”。之后正常可用的 UAPI 数据也无法采集。

**最小修复：** SourceResult 返回实际采集渠道是否使用访客预算，例如 `visitorBudgeted`；成功 TTL 按实际结果确定。失败时结合实际尝试的渠道或缓存中的预算模式确定退避，而非仅按配置 adapter 判断。

**验证：** 不配置 UAPI_KEY，让 60s 失败且 UAPI 成功；返回的 `nextRefreshAt` 至少为 6 小时后，10 分钟后的检查不再次消耗 UAPI 配额。

## 3. [P2] 刷新锁到期后，旧持有者仍可无条件写入快照

**证据：** `lib/feed.ts:20` 在读取 D1 之前固定 `now`，`lib/feed.ts:29` 使用 `now + 55_000` 设置锁租期；采集期间没有续租或总时限。`lib/feed.ts:69` 持久化写入只检查本地 `locked` 布尔值，不再检查当前锁 owner 与有效期。仅删除锁时在 `lib/feed.ts:70` 验证 owner。

**实际后果：** D1 读取、预算写入及多轮采集一旦累计越过租期，另一个隔离实例可以取得锁；旧请求随后仍能提交快照。较慢的旧刷新可能覆盖较新的刷新结果，同时产生重复的付费/配额请求。请求级 `inflight` 只约束当前实例，不能避免此跨实例竞态。

**最小修复：** 租期按实际取得锁的时间计算；采集需有小于租期的总体预算或续租。提交写入时以 owner/租期作为条件，或使用递增版本做 fencing，避免过期持有者写入。只扩大 55 秒不能消除无条件旧写入的问题。

**验证：** A 获得锁后阻塞到租期结束；B 获得锁并提交新快照；让 A 恢复。A 的写入必须被拒绝，最终缓存保持 B 的版本。

## 4. [P2] JSON 可解析但结构损坏时，缓存与本机视图可使整页失败

**证据：** `lib/feed.ts:24` 对持久快照只执行 `JSON.parse`；例如 `{}` 被加入 cache 后，`lib/feed.ts:27` 会读取不存在的 `status.nextRefreshAt` 并抛错，API 最终返回整体 503。`components/trend-app.tsx:61` 对本机视图只验证 id、name、filters 及两个数组；`components/trend-app.tsx:104` 原样把保存的 filters 传给 `setFilters`。缺失或非字符串 query 随即在 `lib/explore.ts:6` 的 `f.query.trim()` 触发渲染错误。本机收藏也只验证了部分字段，未验证历史中的 `at/rank`。

**实际后果：** 单份结构不兼容/损坏缓存不能被隔离，会阻断全部来源；旧版或损坏的本机视图在点击后可令界面崩溃。当前“缓存已损坏，将重新采集”仅覆盖 JSON 语法损坏，未覆盖合法 JSON 的结构损坏。

**最小修复：** 在持久快照、本机 Item 与 SavedView 边界分别做结构归一化；逐条丢弃损坏记录，并合并完整 DEFAULT_FILTERS。验证有限数值、枚举、history 每个元素和 URL；同一条记录损坏不影响其他数据。设置存储版本方便迁移。

**验证：** 将一个 D1 payload 设为 `{}`，其余正常来源仍可获取且该来源重采；将本机视图 filters 设为 `{topics:[],platforms:[]}` 后点击，恢复默认条件或拒绝该条，不能出现应用错误。

## 5. [P2] 取消已到期的自动刷新后，下一次轮询立即重启

**证据：** `components/trend-app.tsx:54` 对 reason=`cancel` 不设置新的 `nextAt`；`components/trend-app.tsx:109` 的取消按钮只 abort 当前请求。自动刷新在 `components/trend-app.tsx:72` 每 15 秒检测 `Date.now() >= nextAt`。一次到期刷新被取消后，`nextAt` 仍为过去时间。

**实际后果：** 用户取消一轮自动刷新后，最多 15 秒就再次启动同样的请求，倒计时持续为 0。这使取消很难达到暂停本轮并等待下个正常周期的目的。

**最小修复：** 显式取消时，把下一轮检查推迟至正常间隔或明确的取消退避时间；或者同时关闭自动刷新并在 UI 说明。保留当前 feed，不改动最近成功时间。

**验证：** 让自动刷新到期并保持慢响应，点击取消；观察至少一个正常检查间隔，不能在下一个 15 秒 tick 就重新发出请求。

## 本次未发现的注入问题及审查限度

来源标题/摘要使用 React 文本节点展示，没有 `dangerouslySetInnerHTML` 或执行来源指令。来源 URL 在 normalize 中限定为 HTTP/HTTPS 且拒绝用户名/密码；外链使用 `noopener noreferrer`。CSV 已对开头为 `= + - @ Tab CR` 的值加前缀。上述路径未发现可直接执行来源脚本的问题；这不等同于完整安全测试。

跨平台原始互动指标没有相加，界面公开了样本位置分公式和地区含义，X 等未接入源未用演示数据伪装。无需为这些已有透明说明额外增加拦截。浏览器与后台的实际测试由主代理完成。
